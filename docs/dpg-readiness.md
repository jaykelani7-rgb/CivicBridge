# CivicBridge adaptation and operations

CivicBridge has four Python services: Citizen Channels receives consented reports and private media; AI Normalization transcribes, translates, extracts, and queues uncertain results; Data Intelligence groups reports and calculates deterministic hotspot scores with versioned evidence; Policy & Impact stores human recommendations, decisions, projects, and measurements. The Next.js frontend uses Firebase server sessions and server-side role checks before calling staff APIs. Event envelopes connect the services locally or through authenticated Pub/Sub push. This is an implementation profile, **not** a Digital Public Good certification claim.

Country packs currently cover India, Brazil, and South Africa as **demonstration** configurations. Their fixture geography and indicators must not be presented as official. Frontend public-language support includes English, Hindi, and Portuguese; speech and translation depend on provider language/model availability and have not been live-smoke-tested here. Location aliases, boundaries, language strings, scoring weights, administrative rules, and official-data crosswalks must be reviewed by a local team before adaptation. The [Cape Town assessment](pilot/README.md) records one blocked official-data join.

For local work, install each service's requirements into a Python environment, copy `.env.example` to a local `.env`, and use SQLite files under `data/`. Set `CITIZEN_DATABASE_URL`, `NORMALIZATION_DATABASE_URL`, and `POLICY_DATABASE_URL` to distinct local file paths. Set `CITIZEN_MEDIA_DIR` to a private directory, install `ffmpeg` for compressed-audio duration checks, set `CITIZEN_INTERNAL_TOKEN` for local service-to-service media access, and explicitly set `USE_MOCK_SERVICES=true` and `ENABLE_MOCK_STUBS=true` only for demo/test mode. The frontend runs with `cd frontend && npm install && npm run dev`; its Firebase session settings and Cloud Run URLs follow the existing README. Apply the additive SQL migrations before starting services:

```sh
python3 scripts/migrate_platform.py --service citizen --database-url data/citizen_channels.db
python3 scripts/migrate_platform.py --service normalization --database-url data/ai_normalization.db
python3 scripts/migrate_platform.py --service policy --database-url data/policy_impact.db
```

Each command accepts a PostgreSQL URL in place of a local path. The version ledger makes reruns harmless, and `CREATE TABLE IF NOT EXISTS` retains existing rows. Keep backups before migrating old installations.

For production, use PostgreSQL URLs for all three repositories, a private `CITIZEN_MEDIA_BUCKET` with restricted service-account access, Cloud Run IAM between services, and `PUBSUB_PUSH_AUDIENCE` plus `PUBSUB_PUSH_SERVICE_ACCOUNT` for OIDC-verified push. Enable `AI_AUTHENTICATE_CLOUD_RUN` and `POLICY_AUTHENTICATE_CLOUD_RUN` when their upstream services require IAM. Disable AI/policy mocks. Use the existing Data Intelligence PostgreSQL/BigQuery migration and versioned dataset-manifest workflow; no production resources were created by this work. Deploy additive schema changes before switching traffic, then verify read/write and replay behavior against a staging backup. Only successful required writes should receive acknowledgments. Citizen intake keeps stable created-event IDs and replays unpublished records on startup or through authenticated `POST /internal/v1/events/replay`. Operators still need scheduled reconciliation, dead-letter queues, and transactionally coordinated publication before relying on delivery under all failure modes. Keep connection pools, backups, and secret rotation under the deployer's control.

To connect the event chain, create the configured topics and authenticated push subscriptions. Route `request.created.v1` and `request.confirmed.v1` to AI Normalization `/internal/v1/events/pubsub`. Route `request.normalized.v1` to Data Intelligence's existing authenticated consumer and to Citizen Channels `/internal/v1/events/pubsub`; route `request.needs_review.v1` to Citizen Channels as well. Route Data Intelligence `hotspot.updated.v1`, Policy & Impact `recommendation.created.v1`, `policy.decision.recorded.v1`, `project.status.updated.v1`, and `impact.metric.updated.v1` to Citizen Channels' push endpoint. Set each push subscription's OIDC audience to its destination URL, use its configured service account, and grant only the required invoker and publisher permissions. A local `CITIZEN_INTERNAL_TOKEN` supports internal media and push tests; production push requires the OIDC identity settings. These subscriptions were not created or tested against a cloud project.

The Telegram adapter uses `TELEGRAM_BOT_TOKEN` and `TELEGRAM_WEBHOOK_SECRET`; its webhook is `/v1/channels/telegram/webhook`. Register it with Telegram's `setWebhook` using the same `secret_token` so Telegram sends `X-Telegram-Bot-Api-Secret-Token`. The bot expects `/country`, `/language`, `/area`, and explicit `/agree` before a text or voice report. It replies with a request tracking ID. Configure an HTTPS webhook URL, a private token/secret, and appropriate Telegram privacy text before activation. The [Telegram Bot API](https://core.telegram.org/bots/api) documents the header, `getFile`, and webhook retries. Local tests stub Telegram; no live bot, webhook, or user message was exercised.

Private citizen text, media, corrections, and confirmation notes are separate from public status DTOs. Internal media retrieval requires the shared service token locally and private Cloud Run/service access in production. Staff routes verify server sessions and roles. Public tracking exposes status and broad linked identifiers, not raw audio, notes, or personal text. There is presently **no automated retention or deletion workflow**; operators must establish retention periods, deletion requests, backup expiry, and applicable local privacy/legal requirements before operating with real citizen data. Access logs and exports also need an owner policy. UI metrics identify manual entry and do not infer causal impact. An independent verification process is an operational decision.

To adapt a new country, add a reviewed country pack and language support, map authoritative boundary/version IDs, supply source manifests with publisher rights and temporal coverage, validate joins and transformations locally, configure provider model availability, review score weights with local practitioners, then test the full citizen-to-project event chain and authorization roles. Do not relabel fixtures as official evidence.
